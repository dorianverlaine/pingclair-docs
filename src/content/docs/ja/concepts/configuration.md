Pingclairfile は読み込み時に一度だけコンパイルされ、サーバーが実行する状態になります。ここから 2 つのことが導かれ、Pingclair の挙動の大部分はこれで説明できます。まず、アドレスの解析やマッチャーのコンパイルのように設定だけで決められる処理は、リクエストのたびにではなく、最初のリクエストより前に済ませます。次に、満たせない設定があれば、誰も試していないリクエストで後になって誤動作するのではなく、読み込みの時点でサーバーが止まります。このページの対象は **v0.2.0-rc.3** です。

## 🗂️ ファイルはグローバルオプションとそれに続くサイトブロックでできている

```caddyfile
{
    email admin@example.com
}

example.com {
    encode zstd gzip
    reverse_proxy 10.0.0.10:8080 10.0.0.11:8080
}

:8080 {
    file_server ./public
}
```

- **グローバルオプション**はファイル先頭の無名ブロックに書きます。ACME アカウントのメールアドレス、Admin API、自動 HTTPS、信頼するプロキシ、ホスト名で指定したアップストリームの DNS 再解決など、特定のサイトに属さない設定を扱います。一覧は[ディレクティブリファレンス](/ja/reference/directives/#global-options)にあります。
- **サイトブロック**はアドレスで名前を付けます。アドレスはホスト、ポート、またはその両方です。ポートは独立したディレクティブではなくアドレスの一部なので、アドレスとリスナーが食い違うことはありません。
- **ディレクティブ**はサイトブロックの中に書く文です。引数を取るもの、入れ子のブロックを取るもの、その両方を取るものがあります。
- **コメント**は `#` から行末までです。
- **空白を含む値は引用符で囲みます。** 期間には単位を付けます。`30s` は 30 秒で、期間が必要な箇所に単位の無い `30` を書くと拒否されます。

## 🧭 マッチャーはディレクティブを適用するリクエストを選ぶ

名前付きマッチャーは `@name` で宣言し、ディレクティブの後ろにその名前を書いて使います。

```caddyfile
example.com {
    @api path /api/*
    header @api Cache-Control "no-store"

    @assets path /assets/*
    header @assets Cache-Control "public, max-age=31536000, immutable"
}
```

`handle` ブロックは 1 つのルートのディレクティブをまとめます。リクエストに応答する `handle` ブロックは 1 つだけで、マッチャーの無い `handle` は、他のどれにも当てはまらなかったリクエストをすべて受け止めます。

```caddyfile
example.com {
    handle /assets/* {
        file_server ./assets
    }

    handle {
        respond "Page Not Found" 404
    }
}
```

## 🚦 どのルートがリクエストに応答するか

サイト内の複数のルートが同じリクエストにマッチしたときは、どれか 1 つが応答しなければなりません。v0.2.0-rc.3 では、ファイル内のどこに書かれていても、最も具体的なパスを持つルートが選ばれます。

📌 **次のリリース（互換性のない変更）。** `main` では、代わりに Caddy のディレクティブ順序に従います。ディレクティブは種類ごとに順位が決まっており（たとえば `respond` は `file_server` や `reverse_proxy` より上位です）、その順序で最初にマッチしたルートが応答します。上位の種類の広いルートより下に狭いルートを書き、それに頼っているサイトは、アップグレード後に別の応答を返すようになります。どちらのバージョンでも従来の応答を保つ方法は 2 つあります。上の例のように各ルートを専用の `handle` ブロックに入れるか、書いた順序を保つ `route` ブロックにルートを並べるかです。完全な順位は [CHANGELOG](https://github.com/dorianverlaine/pingclair/blob/main/CHANGELOG.md) の Unreleased に記録されています。

## 🧩 スニペットとインポートで設定を再利用する

スニペットは `(name) { ... }` として宣言し、`import name` で挿入する再利用可能な断片です。呼び出し側は引数とブロックを渡すことができ、スニペットは `{block}` と書いた位置でそのブロックを受け取ります。

```caddyfile
(site) {
    https://{args[0]} {
        {block}
    }
}

import site example.com {
    reverse_proxy 127.0.0.1:3000
}
```

インポートしたファイルで定義されたスニペットは、それ以降のインポートから参照できます。ディレクティブの引数リストの中にプレースホルダーを書くと拒否されます。Caddy はスニペットを挿入した後にその行を読み直しますが、Pingclair のパーサーにはそれができないため、行の意図を推測する代わりに、できないことをそのまま伝えます。

## 🛡️ 検証はサーバーにできないことを拒否する

`pingclair validate` はファイルをコンパイルし、構文だけでは判断できない検査を行います。ディレクティブの引数、マッチャーの構文、証明書と鍵のファイルが存在するか、そしてクライアントの識別ヘッダーをどのピアが設定してよいかといったポリシー上の制約です。

これらの検査に通らない設定は実行されません。何が失敗するかは 3 つの規則で決まります。

- **実装されていない名前は、名前を挙げて拒否されます。** Pingclair は Caddyfile 形式が定義するすべての名前を認識します。実装していない名前には機能が無いことを伝えるメッセージを出し、タイプミスと取り違えることも、黙って無視することもありません。
- **満たせないオプションは、格下げではなく拒否されます。** ストリーミング対応の Brotli エンコーダーが無いため、`encode br` はコンパイルエラーになります。サーバーが黙って gzip で代用することはありません。
- **構文が正しくても、存在しないファイルを指していればエラーです。** サーバーリポジトリの `examples/full_featured.pingclair` は構文としては正しいものの、そこに書かれた証明書パスが存在しないマシンでは `validate` が拒否します。

サーバーはファイルを読み込むとき、再読み込みも含めて、同じ検査を行います。

## 🔁 再読み込みは再起動せずに設定を差し替える

再読み込みは、プロセスを動かしたままファイルを読み直してコンパイルし、その結果に差し替えます。新しいファイルのコンパイルに失敗した場合は、以前の設定が引き続き配信します。再読み込みを求める方法は 3 つあります。

- `pc service reload`（または `systemctl reload pingclair`）は、インストール済みのユニットを通じて `SIGUSR1` を送ります。
- `sudo kill -USR1 "$(systemctl show -p MainPID --value pingclair)"` は同じシグナルを直接送ります。
- `pingclair reload` は Admin API を経由し、サーバーの判定を表示します。グローバルオプションの `admin` が必要です。

`systemctl reload` が報告できるのはシグナルが届いたことだけなので、サーバーの判定はユニットのステータス行とジャーナルに出ます。

再読み込みでは適用できない変更もあります。その場合、サーバーは一部だけを適用するのではなく、再読み込みを拒否して以前の設定を保ちます。

- **リスナーの変更。** アドレスの追加・削除・移動や、リスナーの平文と TLS の切り替えには再起動が必要です。待ち受けソケットは起動時に作られるためです。
- **グローバルオプション。** `trusted_proxies` のように起動時に確定するオプションはプロセス全体に適用されるため、グローバルオプションのブロックを変更したら再起動が必要です。
- **証明書の構成。** TLS のホスト名を追加したり、サイトが証明書を得る方法を変えたりするには再起動が必要です。

拒否のメッセージは `listener topology changed (added: …, removed: …)` のように変更内容を示し、`sudo pc service restart` で適用できます。

それぞれの結果がどう見えるかは、[サービスとして動かす](/ja/start/service/#-再読み込みの意味)で示しています。

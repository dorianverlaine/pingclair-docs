Pingclairfile은 로드될 때 한 번 컴파일되어 서버가 실행하는 상태가 됩니다. 여기서
두 가지 결과가 나오며, Pingclair 동작의 대부분은 이것으로 설명됩니다. 주소 파싱이나
매처 컴파일처럼 설정만으로 결정할 수 있는 작업은 요청마다가 아니라 첫 요청 전에
끝납니다. 그리고 지킬 수 없는 설정은 아무도 시험하지 않은 어떤 요청에서 뒤늦게
오동작하는 대신, 로드 시점에 서버를 멈춥니다. 기준 릴리스는 **v0.2.0-rc.3**입니다.

## 🗂️ 파일은 전역 옵션과 그 뒤의 사이트 블록으로 이루어집니다

```caddyfile
{
    email admin@example.com
}

example.com {
    encode zstd gzip
    reverse_proxy 10.0.0.10:8080 10.0.0.11:8080
}

:8080 {
    file_server ./public
}
```

- **전역 옵션**은 파일 맨 위의 이름 없는 블록에 씁니다. ACME 계정 이메일, Admin
  API, 자동 HTTPS, 신뢰할 프록시, 호스트 이름 업스트림의 DNS 갱신처럼 특정 사이트에
  속하지 않는 것을 설정합니다. 목록은
  [디렉티브 레퍼런스](/ko/reference/directives/#global-options)에 있습니다.
- **사이트 블록**은 주소, 즉 호스트나 포트 또는 둘 다로 이름을 붙입니다. 포트는
  별도 디렉티브가 아니라 주소의 일부이므로 주소와 리스너가 어긋날 수 없습니다.
- **디렉티브**는 사이트 블록 안의 구문입니다. 인자를 받는 것, 중첩 블록을 받는 것,
  둘 다 받는 것이 있습니다.
- **주석**은 `#`으로 시작해 줄 끝까지 이어집니다.
- **공백이 들어간 값은 따옴표로 감쌉니다.** 기간에는 단위를 붙입니다. `30s`는
  30초이며, 기간이 와야 할 자리에 단위 없는 `30`을 쓰면 거부됩니다.

## 🧭 매처는 디렉티브를 적용할 요청을 고릅니다

이름 있는 매처는 `@name`으로 선언하고, 디렉티브 뒤에 그 이름을 써서 사용합니다.

```caddyfile
example.com {
    @api path /api/*
    header @api Cache-Control "no-store"

    @assets path /assets/*
    header @assets Cache-Control "public, max-age=31536000, immutable"
}
```

`handle` 블록은 하나의 라우트에 속한 디렉티브를 묶습니다. 한 요청에는 `handle` 블록
하나만 응답하며, 매처가 없는 `handle`은 다른 블록이 잡지 않은 모든 요청을 받습니다.

```caddyfile
example.com {
    handle /assets/* {
        file_server ./assets
    }

    handle {
        respond "Page Not Found" 404
    }
}
```

## 🚦 어떤 라우트가 요청에 응답하는가

사이트 안의 여러 라우트가 같은 요청과 일치하면 그중 하나가 응답해야 합니다.
v0.2.0-rc.3에서는 파일의 어디에 쓰였든 경로가 가장 구체적인 라우트가 이깁니다.

📌 **다음 릴리스**, 호환성이 깨지는 변경입니다. `main`에서는 대신 Caddy의 디렉티브
순서를 따릅니다. 디렉티브는 종류별로 순위가 매겨지며(예를 들어 `respond`는
`file_server`와 `reverse_proxy`보다 앞섭니다), 그 순서에서 처음으로 일치하는
라우트가 응답합니다. 순위가 더 앞선 넓은 라우트 아래에 좁은 라우트를 써 두고 그에
의존하는 사이트는 업그레이드 후 다르게 응답합니다. 두 버전 모두에서 기존 응답을
유지하는 방법은 두 가지입니다. 위 예시처럼 각 라우트를 별도의 `handle` 블록에
넣거나, 쓴 순서를 유지하는 `route` 블록에 라우트를 나열합니다. 전체 순위는
[CHANGELOG](https://github.com/dorianverlaine/pingclair/blob/main/CHANGELOG.md)의
Unreleased 항목에 기록되어 있습니다.

## 🧩 스니펫과 import로 설정을 재사용합니다

스니펫은 `(name) { ... }`로 선언하고 `import name`으로 삽입하는 재사용 가능한
조각입니다. 호출하는 쪽은 인자와 블록을 넘길 수 있으며, 스니펫은 `{block}`을 쓴
자리에 그 블록을 받습니다.

```caddyfile
(site) {
    https://{args[0]} {
        {block}
    }
}

import site example.com {
    reverse_proxy 127.0.0.1:3000
}
```

import한 파일에 정의된 스니펫은 그 뒤에 오는 import에서 보입니다. 디렉티브의 인자
목록 안에 들어간 플레이스홀더는 거부됩니다. Caddy는 스니펫을 삽입한 뒤 줄을 다시
읽지만 Pingclair의 파서는 그럴 수 없으므로, 그 줄이 무엇을 뜻했는지 추측하는 대신
할 수 없다고 알립니다.

## 🛡️ 검증은 서버가 할 수 없는 것을 거부합니다

`pingclair validate`는 파일을 컴파일하고, 구문 이상의 확인이 필요한 검사를
적용합니다. 디렉티브 인자, 매처 구문, 인증서와 키 파일의 존재 여부, 그리고 어떤
피어가 클라이언트 식별 헤더를 설정할 수 있는지 같은 정책 제약입니다.

이 검사를 통과하지 못한 설정은 실행되지 않습니다. 무엇이 실패하는지는 세 가지
규칙이 정합니다.

- **구현되지 않은 이름은 이름을 밝혀 거부합니다.** Pingclair는 Caddyfile 형식이
  정의하는 모든 이름을 인식합니다. 구현하지 않은 이름은 기능이 없다는 메시지를
  내며, 오타로 오인되거나 조용히 무시되는 일은 없습니다.
- **지킬 수 없는 옵션은 낮춰서 적용하지 않고 거부합니다.** 스트리밍 Brotli 인코더가
  없으므로 `encode br`은 컴파일 오류입니다. 서버가 슬쩍 gzip으로 대신 서비스하지
  않습니다.
- **구문이 맞아도 없는 파일을 가리키면 오류입니다.** 서버 저장소의
  `examples/full_featured.pingclair`는 구문상 올바르지만, 그 안에 적힌 인증서 경로가
  없는 머신에서는 `validate`가 거부합니다.

서버는 리로드를 포함해 파일을 로드할 때마다 같은 검사를 실행합니다.

## 🔁 리로드는 재시작 없이 설정을 교체합니다

리로드는 파일을 다시 읽어 컴파일하고, 프로세스가 계속 실행되는 동안 결과를
교체합니다. 새 파일이 컴파일되지 않으면 이전 설정이 계속 서비스됩니다. 리로드를
요청하는 방법은 세 가지입니다.

- `pc service reload`(또는 `systemctl reload pingclair`)는 설치된 유닛을 통해
  `SIGUSR1`을 보냅니다.
- `sudo kill -USR1 "$(systemctl show -p MainPID --value pingclair)"`는 같은 신호를
  직접 보냅니다.
- `pingclair reload`는 Admin API를 거쳐 서버의 판정을 출력합니다. `admin` 전역
  옵션이 필요합니다.

`systemctl reload`는 신호가 전달되었다는 사실만 보고할 수 있으므로, 서버의 판정은
유닛의 상태 줄과 저널에 나타납니다.

리로드로 적용할 수 없는 변경도 있습니다. 이때 서버는 일부만 적용하지 않고 리로드를
거부한 채 이전 설정을 유지합니다.

- **리스너 변경.** 주소를 추가·제거·이동하거나, 리스너를 평문과 TLS 사이에서
  전환하려면 재시작해야 합니다. 리스닝 소켓은 시작할 때 만들어지기 때문입니다.
- **전역 옵션.** `trusted_proxies`처럼 시작할 때 정해지는 옵션은 프로세스 전체에
  적용되므로, 전역 옵션 블록을 바꾸면 무엇이든 재시작해야 합니다.
- **인증서 구성.** TLS 호스트 이름을 추가하거나 사이트가 인증서를 얻는 방식을
  바꾸려면 재시작해야 합니다.

거부 메시지는 `listener topology changed (added: …, removed: …)`처럼 변경 내용을
밝히며, `sudo pc service restart`로 적용합니다.

각 결과가 어떻게 보이는지는
[서비스로 실행하기](/ko/start/service/#-리로드의-의미)에 있습니다.
